# Reservation-created email integration implementation plan

> **For Codex:** Execute this plan task-by-task, using test-driven development. Keep all work in `fix/au-email-automation-recovery`; do not modify the dirty `feat/vanilla-detail` worktree, push, deploy, or send real email.

**Goal:** Preserve the existing operator booking notification while adding independently idempotent, ledger-backed booking-request receipt email preparation for cake and class reservations.

**Architecture:** The notification Function builds two distinct allowlisted payloads per reservation. Each payload is atomically claimed by creating a private `email_deliveries` pending row keyed by its logical event. Only the caller that creates the row invokes an injected Resend transport; all existing sent, pending, failed, or uncertain records are safely skipped in this task.

**Tech Stack:** Node ESM, Appwrite TablesDB through `node-appwrite`, Appwrite Functions, Resend HTTPS API, Node test runner.
