## D01. 목표와 범위

### 1.1 해결하려는 문제 [확정]

현재 사이트는 글과 정보가 많고 산만하게 느껴진다. 컵케이크 등 일부 상품 사진은 인공적인 인상 때문에 주문하고 싶은 마음이 잘 들지 않는다는 사용자 피드백이 있었다. 이번 작업은 단순한 색상 교체가 아니라 **상품 탐색 → 선택 → 주문**, 그리고 **상담이 필요한 서비스의 이해 → 문의**를 정리하는 개편이다.

목표는 다음 세 가지다.

1. **제품이 먼저 보인다.** 실제 제품·포장·행사 사진을 중심으로 구성한다.
2. **고르는 방법이 단순하다.** 상품 카드, 옵션, 세트, 개별 포장의 관계를 명확히 보여준다.
3. **상담 서비스의 가치가 설명된다.** 커스텀 케이크, 기업 행사, 카페 납품, 컨설팅은 일반 장바구니 상품과 구분한다.

### 1.2 이번 디자인에서 바꾸지 않는 것

기존 주문 데이터, Appwrite 권한·스키마, 가격 계산, 결제 판정, 운영 클래스 공개 상태, HOGIRL publish 상태를 디자인 수정의 부수 효과로 변경하지 않는다. AU 디자인 개편을 이유로 KR 사이트까지 일괄 변경하지 않는다. 상세 실행 경계는 `plan.md` P04·P07을 따른다.

### 1.3 하지 않을 것

- 기존 사이트를 버리고 새로운 프레임워크나 쇼핑몰 플랫폼으로 이전하는 것을 전제로 하지 않는다.
- Next.js, Tailwind, 새로운 UI 라이브러리, 새 폰트를 레퍼런스 문서에 나온다는 이유만으로 설치하지 않는다.
- ACME의 브랜드명·상품 사진·문구를 실제 베리굿 콘텐츠로 사용하지 않는다.
- 실사 촬영이 필요한 부분을 무단 생성 이미지로 대체하지 않는다.
- 미정 상품 가격·납기·배송·최소 주문량·예약금 비율을 그럴듯하게 만들어 넣지 않는다.
- 로그인·검색·결제가 아직 연결되지 않았는데 실제 기능처럼 공개하지 않는다.

## D02. 자료의 우선순위와 충돌 처리

### 2.1 디자인 판단 순서

1. 사용자의 가장 최근 명시적 결정과 그 결정이 기록된 이 문서.
2. 사용자가 승인한 Pencil 프레임과 그 승인 버전.
3. 보존 대상으로 지정한 현재 폰트·호랑이 벽지·로고 자산.
4. ACME 레퍼런스의 구조와 첨부 스타일 문서.
5. 과거 디자인 MD는 이력과 자산 위치를 이해하기 위한 참고 자료.

기존 기능·권한·주문 계약은 이 우선순위로 무효화하지 않는다. 디자인과 기능 계약이 충돌하면 아스트라가 영향과 대안을 제시하고 별도 승인을 받는다.

### 2.2 첨부 ACME 문서의 성격 [확인]

원문은 [references/acme-style-reference.md](./references/acme-style-reference.md)에 그대로 보관한다. 원문은 수치가 정규화되어 있고, 역할·추천 사항은 해석이며, HTML 예제는 원본 컴포넌트가 아닌 재구성이라고 밝힌다. 따라서 `148px`, `3px`, `1440px` 등을 모두 실제 사이트에서 검증된 고정값으로 취급하지 않는다. [S02]

### 2.3 ACME에서 적용할 것과 적용하지 않을 것

| 항목 | 적용 판단 |
|---|---|
| 사진이 중심인 상품 그리드 | 참고한다. 베리굿의 상품 수와 사진에 맞춰 조정한다. |
| 일정한 상품명·가격·옵션 정보 위치 | 참고한다. 긴 한글/영문 상품명도 확인한다. |
| 얇은 선과 여백, 그림자 없는 기본 UI | 기본 방향으로 채택하는 제안이다. |
| 흑백 전용 UI, 회색 canvas | 채택하지 않는다. 흰색·녹색·핑크 기준이 우선이다. |
| Helvetica Neue 전용 | 채택하지 않는다. 현재 폰트 체계를 유지한다. |
| 아이콘·일러스트 금지 | 채택하지 않는다. 시트 설명 아이콘과 호걸이 랭킹 스티커는 요청된 요소다. |
| 모든 UI 대문자, 10px 작은 텍스트 | 그대로 복제하지 않는다. 한글과 모바일 가독성에 맞춰 조정한다. |
| ACME 초대형 워드마크·삼단 레이아웃 | 선택적 참고다. 베리굿에 의무적으로 복제하지 않는다. |
| 원문 CSS/Tailwind 예제 | 참고만 한다. 프로젝트 의존성·전역 CSS 변경 명령이 아니다. |

원문 안에서도 ghost 버튼 중심 설명과 filled action 표기처럼 다른 표현이 있다. 안티가 이를 임의로 통합하지 않고, 실제 베리굿 버튼 시안은 D07의 제안으로 보여주어 승인받는다.

### 2.4 과거 문서와의 충돌 [확인]

이전에 확인한 `docs/prompts/ANTIGRAVITY_VCC_DESIGN.md`, `docs/planning/AU_CAKE_REDESIGN_PLAN.md`, `docs/design/JENISELECT_HOME_DESIGN.md`에는 VCC/Hartzler·청록·노랑·대형 billboard·다른 역할 분담 같은 과거 지침이 남아 있다. 이번 개편에서 해당 시각 지침을 자동 재적용하지 않는다. 파일을 삭제하거나 전체 덮어쓰지는 않는다. [S05]

## D05. 폰트와 호랑이 벽지 보존

### 5.1 폰트 [확정 + 확인]

현재 코드에는 Work Sans 400/700/800과 SUIT Variable이 로드되어 있다. 기본 display/sans는 Work Sans이며, `html:lang(en)`에서 body 폰트를 SUIT Variable로 설정한다. 언어별 최종 적용은 실제 페이지의 `lang`과 스타일 상속을 브라우저에서 확인한다. [S04]

| 역할 | 유지 기준 |
|---|---|
| 제목·디스플레이 | 기존 `--font-display`, `--font-sans` 사용. |
| 본문·폼 | 기존 `--font-body`와 언어별 적용 유지. |
| 로고 | 기존 로고 자산 사용. 일반 글자로 임의 재작성하지 않는다. |
| 한글 대체 폰트 | 현재 fallback 체계 유지. 새 외부 폰트를 임의 추가하지 않는다. |

폰트 유지가 기존의 큰 글자 크기·대문자·행간까지 모두 유지한다는 뜻은 아니다. 크기·굵기 계층·줄바꿈은 새 쇼핑몰 구조에 맞춰 시안으로 검토한다.

**Pencil에서 폰트가 없거나 대체 폰트가 적용되면:** 다른 글꼴로 조용히 대체하지 않는다. 누락 폰트와 영향을 보고하고 John이 확인할 때까지 해당 프레임을 승인본으로 표시하지 않는다.

### 5.2 호랑이 벽지 [확정]

확인된 기존 자산 위치:

- 데스크톱: `src/assets/tiger-pattern-desktop.webp`
- 모바일: `src/assets/tiger-pattern-mobile.webp`
- 기본 스타일: `src/styles/tokens.css`의 `.home-tiger-background`
- 모바일 적용 확인 위치: `src/styles/chrome.css`

기본 구현은 고정 배경 레이어, 중앙 배치, `cover`, `opacity: 0.09`이다. 모바일 규칙과 현재 노출 페이지 범위는 구현 시작 시 다시 확인한다. [S04, S06]

보존 체크:

- [ ] 원본 이미지 파일을 수정·재생성하지 않는다.
- [ ] 임의 색보정·흑백화·블러·반복 패턴화하지 않는다.
- [ ] 현재 위치·크기 방식·투명도·데스크톱/모바일 자산 선택을 유지한다.
- [ ] 새 기본 흰색 바탕과 결합했을 때의 모습은 시안에서 확인한다.
- [ ] 페이지 전체를 불투명 흰 패널로 덮어 패턴을 숨기지 않는다.
- [ ] 현재 홈에 한정된 배경을 모든 상품·관리자 페이지로 확대하지 않는다.
- [ ] 가격·폼·본문이 읽히는지 확인하고 문제가 있으면 시안 변경을 요청한다.

Pencil에는 잠긴 `Wallpaper / Preserved` 레이어로 두는 방식을 제안한다. 패턴 위에 작은 상품 surface를 쓰는 것은 가능하지만, 벽지의 사실상 삭제로 이어지지 않아야 한다.

```text

  Cakes                                       Corporate & Parties
```

이 명칭과 묶음은 최종 승인 전의 후보다. 기존 클래스·예약 조회·리뷰·연락처는 사라지지 않게 보조 메뉴나 적절한 기존 동선을 유지한다. 검색·계정 메뉴는 구현 상태에 맞춰 공개하며, 디자인 단계의 미래 기능 표기를 실제 운영 메뉴로 오인시키지 않는다.

| 종류 | 고객에게 보여줄 흐름 |

| 상담·견적이 필요한 서비스 | 사례 보기 → 제작/진행 과정 이해 → 요구사항 접수 → 상담·견적 → 승인된 방식으로 결제/확정 |

예약금·잔금·납기·배송 가능 여부는 디자인이 결정하지 않는다. 기존 요청 접수와 최종 예약 확정이 다르다면 그 차이를 문구에서 보존한다.

### 7.2 버튼

주요 행동은 녹색 채움 + 밝은 글자, 보조 행동은 녹색 테두리 또는 간결한 텍스트 버튼으로 시도한다. 이는 ACME 원문의 ghost-only 규칙을 그대로 따르는 것이 아니라 베리굿 적용안이다.

한 영역의 주요 행동은 한 개를 우선한다. 장바구니 담기, 상담 요청, 결제 등 실제 의미에 맞는 문구를 쓴다. 옵션 미선택·품절·처리 중·오류 상태를 색상만으로 구분하지 않는다.

### 7.3 상품 카드

카드의 기본 정보는 **실제 사진 → 상품명 → 가격/구성 → 필요한 특징 하나** 정도로 제한하는 제안이다. ACME 원문의 정보 위·이미지 아래 배치를 의무적으로 복제하지 않는다. 두 배치 중 더 적합한 것을 실제 사진으로 검토한다.

- 이름이 두 줄이 되어도 가격 위치가 불규칙하게 흔들리지 않게 한다.
- 가격 범위는 승인된 가격 데이터에서 나오게 한다. 임의의 `From` 가격을 만들지 않는다.
- 호걸이 배지는 사진의 주요 장식을 가리지 않는다.
- 상품별 아이콘은 해당하는 특징만 표시한다.
- 수량·옵션 선택이 필요한 상품을 잘못된 기본값으로 즉시 구매시키지 않는다.
- 미정 상품은 시안에서 `검토용`으로 표시하고 운영용 구매 버튼을 붙이지 않는다.

### 7.4 옵션·세트·개별 포장

선택 항목마다 사진, 이름, 구성/수량, 추가 금액, 선택 여부를 같은 순서로 보여준다. 선택 상태는 테두리·표시·텍스트 등으로도 식별된다. 상품 사진을 장식용으로만 바꾸고 실제 주문 옵션은 이전 값으로 남기는 불일치를 금지한다.

개별 포장은 상품별 제공 형태와 비용을 구분한다. 한 장의 포장 사진으로 모든 상품이 같은 포장으로 제공되는 것처럼 표현하지 않는다.

### 7.5 가독성과 접근성 검토

프로젝트 검토 목표는 일반 텍스트 명암비 4.5:1, 큰 텍스트 3:1 이상이다. 실제 대비·초점 표시·키보드 동작·모바일 터치 영역을 함께 검토한다. 이는 이 문서가 접근성 인증을 완료했다는 뜻이 아니다.

모션은 최소화한다. 첫 시안에 자동재생 영상, 자동 슬라이더, 과도한 등장 효과를 기본으로 추가하지 않는다. 기존 동작을 제거하거나 변경할 때는 별도 영향 검토를 한다.

## D08. 페이지별 디자인 요구

### 8.1 홈

첫 검토 구간은 **헤더 → 대표 제품 사진 → 베스트 3 → 상품군 진입 영역**으로 한다. 이후 서비스 안내·짧은 브랜드 소개·푸터로 확장한다. 이 순서와 섹션 수는 시안 제안이다.

대표 사진 한 장과 짧은 제목·설명·주요 버튼으로 시작한다. 갸또/제누아즈 시트 안내는 짧은 특징 블록이나 상품 배지로 넣고 긴 제조 설명은 상세로 보낸다. 홈페이지에서 커스텀·기업 주문·납품·컨설팅을 모두 길게 설명하지 않는다.

호걸이 랭킹은 **파운드 1위 → 갸또 파베 2위 → 치즈 3위**를 반영한다. 어떤 치즈케이크 SKU인지 확정 전에는 특정 상품 ID와 연결하지 않는다. `Bestsellers`, `Our Picks` 등 제목은 순위의 기준에 맞춰 John이 정한다.

### 8.2 상품 목록

케이크·초콜릿·세트가 섞여도 카드 규칙은 일정하게 유지한다. 데스크톱 열 수는 실제 상품 수·이름 길이로 검토하고 모바일은 2열부터 시도하되 가독성이 나쁘면 변경안을 제시한다.

품목 수가 적은데 복잡한 필터·검색 시스템부터 만들지 않는다. 분류는 현재 데이터로 정확히 구현할 수 있는 것부터 사용한다.

### 8.3 상품 상세

사진 갤러리와 구매 선택 영역을 분명히 구분한다. 사진·제품명·가격·중요 옵션·주문 행동이 우선이며, 긴 설명은 아래쪽으로 정리한다. 기존 상세의 삼단 구성을 모든 상품에 강제하지 않는다.

반드시 포함할 정보:

- 실제 판매 구성과 양을 이해할 수 있는 대표 사진.
- 크기·수량·시트·마감 등 실제 선택 가능한 옵션.
- 초콜릿 추가 구성, 아몬드 세트 등 선택 가능한 사진 옵션.
- 개별 포장 적용 여부와 사진.
- 픽업/제작 안내의 현재 승인된 내용.
- 행사 사진 캡션과 짧은 사용 장면.

알레르기·보관·제조 정보는 실제 상품 자료를 받아 넣는다. 사진이나 상품명에서 재료·함량·인증을 추정하지 않는다.

### 8.4 컵케이크 12구

12구 상자를 열었을 때의 **실제 12개 구성 사진**을 핵심 자산으로 삼는다. 근접 사진, 개별 포장, 행사 배치를 보조 사진으로 둔다. 6개 사진을 반복·합성하여 실제 12구 사진인 것처럼 사용하지 않는다.

### 8.5 초콜릿과 세트

아몬드 초코볼은 80g 단품, 5+1 구성, 검은 통 80g×2를 시각적으로 구분한다. 검은 통 가격은 `%25` 원문을 확인하기 전까지 운영 가격에 넣지 않는다.

파베 초콜릿·에펠탑 초콜릿은 독립 상품으로 디자인한다. 기존 케이크 추가 옵션의 가격·포장 단위를 독립 판매 조건으로 자동 재사용하지 않는다. 제품 ID는 디자인 담당자가 임의로 확정하지 않는다.

### 8.6 커스텀 케이크

기본 메시지는 **레퍼런스를 그대로 복제하는 대신, 고객의 행사와 취향에 맞는 디자인을 만든다**는 것이다.

과정 후보:

```text
좋아하는 레퍼런스 약 3장 전달
→ 행사·인원·원하는 분위기 확인
→ 디자인 방향과 견적 안내
→ 합의된 조건으로 제작
```

제작 사례 → 과정 → 신청 정보 순으로 구성하는 것을 제안한다. 수정 횟수, 스케치 제공, 피규어 제공, 예약금 비율, 디자인 확정 기한을 약속하지 않는다. 가격이 단순히 크기만의 차이가 아니라 상담·디자인·제작을 포함한다는 설명에 집중한다.

검토용 카피 예시: “좋아하는 레퍼런스를 보내주세요. 그대로 복제하는 대신, 원하는 분위기를 바탕으로 당신의 행사를 위한 케이크를 디자인합니다.” 실제 게시 전 John이 문구를 승인한다.

### 8.7 Corporate & Parties

기업 행사를 첫 사용 사례로 배치하고 학교 행사·웨딩·개인 파티를 함께 다룬다. 실제 구성 사진, 인원/수량, 개별 포장, 행사 일정, 전달 방식 문의를 우선한다.

“회사에서 예산을 많이 준다”는 대화상의 영업 방향을 검증된 시장 통계나 고객 대상 문구로 옮기지 않는다. 기업 로고 부착, 전국 배송, 대규모 공급 가능 수량도 제공 능력이 확인된 경우에만 표시한다.

### 8.8 Café Supply

홀케이크 라인업과 쇼케이스/진열 실사를 보여준다. 카페에서 판매할 모습을 이해할 수 있는 사진이 중요하다. 도매가·최소 주문량·정기 배송 주기·서비스 지역은 확인 전 공개하지 않는다.

R08과 R11은 같은 납품 서비스 요구다. 메뉴명과 페이지명만 다르게 만들어 중복 문의 시스템을 만들지 않는다.

### 8.9 Menu & Experience Direction / 컨설팅

메뉴·진열·패키징·고객 경험 디렉팅을 설명하는 방향을 제안한다. 실제 서비스 범위와 기존 포트폴리오를 John/Jenny가 확인한다. 초기 미팅, 2주·4주 프로그램 등 이전에 논의된 조건은 이번 대화에서 가격까지 재확정되지 않았으므로 자동 게시하지 않는다.

초기 상담료만 공개할지, 상담 예약에 바로 결제를 붙일지는 `plan.md`의 미확정 항목으로 관리한다.

### 8.10 장바구니·결제·로그인

장바구니에는 상품별 수량, 선택 옵션, 세트 구성, 포장비가 보인다. 고객이 수정했을 때 합계·주문 데이터·사진 표시가 함께 맞아야 한다.

비회원 주문을 기본으로 유지한다. 로그인은 “다음 주문을 편하게 하기 위한 선택 기능”이다. 로그인 상태가 아니라고 주문을 막는 디자인으로 만들지 않는다.

결제 UI는 성공 화면만 만들지 않는다. 처리 중, 취소, 실패, 확인 중, 가격/가능 일정 변경, 재시도 상태를 포함한다. **PayPal 창이 닫힌 것과 결제가 완료된 것을 같은 상태로 표현하지 않는다.** 세부 판정은 코덱스 계약을 따른다.

### 자산 운영 규칙

사진 원본은 보존하고 웹용 파생본을 별도로 만든다. 파일 이름만으로 상품을 매칭하지 않고 상품/옵션 ID·캡션·사용 페이지·실사 여부를 함께 기록한다. 큰 원본 전체를 Git에 올리는 방식은 저장 정책을 정한 뒤 판단한다.

Pencil에서 참조하는 이미지는 상대 경로 또는 팀이 재현 가능한 안정된 위치를 사용한다. 임시 다운로드 URL이나 한 사람의 맥 절대 경로만으로 구성하지 않는다. 없는 원본은 필요한 구도·비율을 적은 명확한 placeholder로 두고 승인본/운영 이미지로 표시하지 않는다.

캡션 예시는 `60th birthday celebration`, `Individually packed for a corporate event`처럼 용도가 분명한 방향이다. 실제 사례가 아니면 그 사실을 구분한다. 대체 텍스트는 사진 내용을 설명하고, 캡션은 용도를 설명하되 같은 문구를 기계적으로 반복하지 않는다.

## D11. Pencil 작업 방식과 파일 구성

### 11.1 원본 위치 [제안]

```text
<FRONTEND_WORKTREE>/
├── design/
│   └── au-site-redesign.pen
└── docs/redesign/
    ├── design.md
    ├── plan.md
    ├── references/
    │   ├── acme-style-reference.md
    │   └── brand-palette.png
    └── evidence/                 # 승인된 캡처·노드 정보·대조 자료를 추후 보관
```

`<FRONTEND_WORKTREE>`는 맥북에서 확인한 실제 경로로 지정한다. 이 예시는 현재 존재하는 디렉터리라고 주장하는 것이 아니다. 기존 `consulting.pen`, `footer-design.pen` 등의 이름만 보고 새 개편 원본으로 사용하거나 덮어쓰지 않는다.

### 11.2 편집 가능한 구조

- 화면 전체를 이미지 한 장으로 만들지 않는다.
- 텍스트, 가격, 버튼, 배지, 이미지 영역을 개별 수정 가능한 요소로 만든다.
- 색상·간격·글자 역할은 이름 있는 변수/스타일로 관리한다.
- 상품 카드·버튼·옵션 tile은 재사용 가능한 컴포넌트로 구성한다.
- 배경은 `Wallpaper / Preserved`, 화면 상태는 별도 프레임으로 명명한다.
- John이 사진, 크기, 간격, 문구를 직접 바꿀 수 있어야 한다.
- 사용 중인 Pencil 기능·MCP 이름은 실제 연결에서 확인한다. 도구 이름을 추정하지 않는다.

### 11.3 프레임 계획

| 프레임 | 내용 | 제작 시점 |
|---|---|---|
| F00 — Readme & Decisions | 기준 문서 버전, 폰트, 색, 미정 항목 | 1차 |
| F01 — Foundations | 컬러, 글자 계층, spacing, 버튼 | 1차 |
| F02 — Components | 카드, 랭킹 배지, 시트 아이콘, 옵션 tile | 1차 |
| F03 — Home / Desktop 1440 | 헤더·히어로·베스트·카테고리 우선 | 1차 |
| F04 — Home / Mobile 390 | 동일 정보의 모바일 흐름 | 1차 |
| F05 — Shop / Desktop & Mobile | 상품 목록과 분류 | 홈 승인 후 |
| F06 — Product Detail / Desktop & Mobile | 사진·옵션·포장·관련 상품 | 카드/계약 승인 후 |
| F07 — Custom / Events / Supply / Direction | 서비스별 핵심 레이아웃 | 서비스 구성 승인 후 |
| F08 — Cart & Checkout States | 장바구니·PayPal 상태 | 계약 검토 후 |
| F09 — Optional Account States | 선택 로그인·정보 불러오기 | 인증 방식 검토 후 |

모든 프레임은 `draft / john-review / approved / superseded` 중 하나의 디자인 상태를 가진다. 이 디자인 상태는 HOGIRL 콘텐츠의 draft/published와 별개다.

### 11.4 한 번에 한 명만 편집

안티 제작 → 저장·편집 종료 → John 수정 → 저장·승인 → 안티가 다시 읽기 순서로 인계한다. John과 안티가 같은 `.pen`에 동시에 쓰지 않는다. 아스트라는 승인 버전을 읽고 검토하며 디자인 원본을 직접 재작성하지 않는다.

인계할 때 파일 절대 경로, Git 커밋/미커밋 상태, 파일 해시 또는 수정 시각, 프레임 이름·노드 ID를 전달한다. 구현은 변경 가능한 '최신' 파일이 아니라 **승인된 버전**을 기준으로 한다.

## D13. 디자인 승인·구현 대조 기준

### 13.1 디자인 승인에 필요한 증거

- 지정된 `.pen` 전체 경로와 승인 버전 식별자.
- 데스크톱/모바일 프레임 이름·노드 ID·캡처.
- 실제 사용 폰트와 대체 발생 여부.
- 호랑이 벽지 원본·표현 보존 여부.
- 실사/placeholder 구분과 미확정 가격·카피 목록.
- John의 승인 범위: 홈만인지, 카드까지인지, 상세까지인지.

### 13.2 구현 대조 체크

- [ ] 흰색 바탕과 녹색·핑크 역할이 시안과 일치한다.
- [ ] `#352F31`/`#362F31`의 선택이 최종 승인 기록과 일치한다.
- [ ] 기존 폰트와 언어별 역할을 유지한다.
- [ ] 호랑이 벽지를 없애거나 흐리게/진하게 변경하지 않았다.
- [ ] 상품 사진의 구성·수량·비율·캡션이 실제 판매 조건과 맞는다.
- [ ] 12구 컵케이크와 개별 포장 사진이 요청된 위치에 보인다.
- [ ] 옵션 선택, 사진, 합계, 주문 요약이 서로 일치한다.
- [ ] 모바일에서 중요한 버튼·가격·옵션이 잘리거나 가려지지 않는다.
- [ ] 메신저·동의 배너·고정 버튼이 서로 겹치지 않는다.
- [ ] 한글/영문 긴 문구, 큰 글자 설정, 키보드 초점을 확인했다.
- [ ] HOGIRL draft, 기존 클래스·예약·관리자 기능에 임의 변경이 없다.
- [ ] 시안과 다른 점 및 알려진 미완료 사항이 인수인계에 적혀 있다.

디자인 대조 통과와 백엔드 테스트 통과는 별도 결과다. 어느 하나로 다른 검증을 대신하지 않는다.
