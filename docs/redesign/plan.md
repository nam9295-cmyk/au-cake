# AU-CAKE 리디자인 — Implementation Plan

> **에이전트 실행자:** 승인된 Task를 순서대로 실행한다. Superpowers를 사용하는 실행자는 `executing-plans` 또는 독립 하위 작업에 적합한 `subagent-driven-development`를 사용하되, 이 문서의 역할 분담·승인 경계를 우선한다.  
> **문서 ID:** AU-REDESIGN-PLAN · **버전:** 1.0 · **정리일:** 2026-09-20 (Asia/Seoul)  
> **권장 저장 위치:** `docs/redesign/plan.md`  
> **Spec:** [design.md](./design.md) v1.0  
> **상태:** 사용자 요구를 종합한 **검토용 전체 실행 계획**. 문서 요청은 시안·제품 코드·DB 변경·실결제·운영 공개의 일괄 승인이 아니다.

**Goal:** 현재 예약 기능과 데이터를 보존하면서 AU 사이트를 실사 상품 중심 쇼핑몰과 맞춤 제작·기업 주문 상담 사이트로 개편한다.

**Architecture:** 기존 React·TypeScript·Vite·Appwrite 구조를 유지한다. Pencil에서 시각 기준을 먼저 확정하고, 상품·주문 계약을 경계로 프론트와 백엔드 작업을 나눈다. PayPal은 먼저 연결하고 Stripe는 후속으로 분리하며, 선택적 고객 로그인은 기존 관리자 인증과 명확히 구분한다.

**Tech Stack:** 현재 저장소의 React, TypeScript, Vite, Appwrite, CSS. 디자인은 Pencil/pen.dev. 맥북의 Antigravity·Codex를 Herdr로 조정하는 운영안. 실제 설치 버전과 CLI/MCP 연결은 착수 시 확인한다.

**Global Constraints:** 바탕 `#FFFFFF`; 메인 `#1F5A46`; 강조 `#EDC5C4 / #F05D88 / #B02E3B`; 글자색 시안 기준 `#352F31` 및 기존 `#362F31` 차이 기록; 기존 폰트·호랑이 벽지 보존; HOGIRL draft 유지; AU/KR·기존 주문 호환성 보호; 강제 삭제·무단 배포 금지.

**Review Focus:** 새 프론트와 구 API의 일시적 공존, 5+1·세트·개별 포장의 수량/금액 불일치, 결제 성공 후 응답 유실, 고객 인증 도입으로 인한 관리자 권한 확장, 다른 worktree/원본 이미지 손실을 각각 검증한다. 담당은 T08·T10·T13·T14·T02다.

또한 draft/noindex는 비밀 데이터의 접근 제어와 같지 않다. 번들·미디어 URL·외부 저장소의 접근 정책은 별도로 확인하며, 이번 디자인 작업에서 임의 ACL 변경이나 콘텐츠 삭제를 하지 않는다.

`src/App.tsx`, route/type/catalog/cart/repository, 공유 CSS 토큰, `package.json`, lockfile, 배포 설정은 **사전 조정 파일**이다. 두 사람이 동시에 수정해야 한다면 작업을 순차화하거나 파일 소유자를 명시하고 PR을 나눈다.

## P05. Git과 worktree 운영안

### 5.1 기본 형태 [제안]

```text
main                             ← 현재 운영 기준. 승인된 hotfix/최종 공개만 반영
└─ feat/au-site-redesign          ← 개편 통합. Astra가 조정
   ├─ feat/au-redesign-pencil     ← 초기 시안 문서·자산 작업
   ├─ feat/au-redesign-ui-shell   ← 승인된 홈·공통 UI
   ├─ feat/au-redesign-catalog    ← 상품·세트 계약 및 구현
   ├─ feat/au-redesign-services   ← 서비스 기능 작업 시 생성
   ├─ feat/au-redesign-paypal     ← PayPal 단계에서 생성
   └─ feat/au-redesign-account    ← 선택 로그인 단계에서 생성
```

브랜치를 모두 미리 만들지 않는다. 지금 수행할 Task만 만들고 끝난 작업은 검증 후 종료한다. 새 Task는 매번 처음 baseline에서가 아니라 **최신 검증된 통합 SHA**에서 시작한다.

맥북에서는 같은 저장소의 **별도 checkout/worktree**를 안티와 코덱스에게 배정한다. worktree는 파일·HEAD·index를 분리하지만 refs 등 저장소 일부는 공유한다. 따라서 두 사람이 같은 브랜치를 함께 관리하거나 전역 Git 정리를 수행하지 않도록 한다. [P-S08]

### 5.2 실제 경로 등록

```text
Mac repository root: 착수 시 확인하여 P14에 기록
Frontend worktree: 착수 시 생성/확인하여 P14에 기록
Backend worktree: 착수 시 생성/확인하여 P14에 기록
Integration worktree: 필요 시 별도 등록
Pencil canonical file: <Frontend worktree>/design/au-site-redesign.pen
Server read-only/audit copy: /home/john/workspace/au-cake 또는 승인된 별도 검증 경로
```

동기화 클라우드 폴더에 Git 작업본을 두거나 작업 디렉터리 전체를 덮어쓰는 전달은 피한다. 코드는 commit/push/fetch로, 큰 원본 사진은 승인된 자산 저장 방식으로 전달한다. 개발 서버 포트·빌드 출력·테스트 임시 디렉터리를 구분한다.

### 5.3 변경 금지 규칙

- `main`에 직접 개발 commit을 만들지 않는다.
- 서로 같은 실제 폴더에서 동시에 파일·index·branch를 변경하지 않는다.
- 다른 에이전트의 변경을 포함할 수 있는 무검토 `git add .`를 사용하지 않는다.
- `git reset --hard`, `git clean -fdx`, 강제 push, `git branch -D`, 강제 worktree remove를 사용하지 않는다.
- 공유 브랜치의 rebase/이력 재작성은 기본 금지. 필요하면 별도 승인·조정한다.
- 충돌을 `ours/theirs` 일괄 선택으로 덮지 않는다. 관련 쓰기를 멈추고 한 명이 해결한다.
- 현재 단계와 무관한 브랜치·worktree를 정리하지 않는다.

### 5.4 PR과 merge

작업 branch → 통합 branch에 작은 PR → Astra 검토 → 통합본 테스트 → John의 시각 확인 순서로 진행한다. 기본 PR base는 `feat/au-site-redesign`이며, 운영 hotfix만 별도 main 경로를 사용한다.

저장소 정책이 허용하면 작업 branch의 일반 merge로 ancestry를 보존하는 것을 제안한다. squash가 필요하면 그 사실과 원본 head를 기록하고, 병합된 작업 branch를 다음 작업에 재사용하지 않는다. `git branch -d`가 거부되면 보존·보고하고 강제 삭제하지 않는다.

브랜치 보호·필수 검사·main 자동 배포·preview branch 설정을 먼저 읽고 기록한다. 이 문서의 권장 설정을 실제로 적용했다고 간주하지 않는다.

### 5.5 운영 hotfix

운영 긴급 수정은 별도 hotfix에서 검토·승인 후 main에 반영한다. 그 후 동일 변경을 개편 통합본에도 반영한다. **개편 시작 후에도 main이 영원히 `40ac23c`여야 한다는 뜻은 아니다.** baseline tag는 보존하고, 최신 운영 변경과 개편 작업이 다시 합쳐지도록 관리한다.

### 5.6 완료 후 정리

정리 전 tracked·untracked·ignored·stash·외부 사진 원본·미전달 결과를 확인한다. clean은 ignored 파일이 없다는 뜻이 아니다. 태그/원격 커밋이 보존된 것을 확인하고, 정상 worktree remove와 `git branch -d`가 가능한 대상만 정리한다.

## P06. Herdr 운영과 세션 기억

### 6.1 Herdr의 역할

Herdr는 에이전트 실행 위치·상태·프롬프트·결과 전달을 관리하는 도구로 사용한다. 공식 문서에는 Codex와 Antigravity CLI 지원 및 에이전트에 작업을 전달하고 결과를 읽는 흐름이 있다. 다만 GUI 안티의 채팅과 CLI가 동일 세션·MCP 설정이라고 가정하지 않는다. [P-S09, P-S10]

설치 버전과 실제 `--help`를 확인하고 실행 명령·pane ID를 추정하지 않는다. 반환된 실제 pane/agent 식별자를 사용한다. 이 문서는 Herdr가 현재 설치·실행 중임을 확인한 보고서가 아니다.

### 6.2 기본 운영

안티 1명과 맥북 아스트라 1명으로 시작한다. 초기 디자인 중 코덱스는 읽기 전용 계약 분석과 검토에 집중한다. 독립 가능한 큰 작업이 생길 때만 Terra/Luna 등 추가 작업자를 제한된 파일 범위로 붙인다.

**Herdr 메시지 = 조정 통로. Git 커밋과 기준 문서 = 확정 결과.** 대화가 자동으로 모든 에이전트 기억에 동기화된다고 가정하지 않는다.

### 6.3 결과 전달 형식

```text
Task ID / 담당자:
기준 문서 버전 / 기준 commit:
결과 branch / commit:
변경 파일:
허용 범위 밖 변경 유무:
디자인 frame·node 또는 계약 버전:
실행한 검증과 결과:
미완료·실패·질문:
다음 담당자가 할 일:
```

Herdr의 `done`은 검증·승인·merge 가능 판정이 아니다. 해당 Task 결과 커밋·테스트 종료 코드·화면 증거를 확인해야 한다. [P-S10]

### 6.4 “항상 참고”를 위한 프로젝트 규칙 연결

T00에서 기존 `AGENTS.md` 및 안티 프로젝트 규칙 파일의 존재와 실제 지원 방식을 확인한다. 있다면 기존 내용을 덮어쓰지 말고 아래 취지의 링크를 추가하는 문서 변경을 검토한다. 없다면 사용 중인 클라이언트가 읽는 위치를 먼저 확인한다.

```text
AU-CAKE redesign 작업 전 docs/redesign/plan.md P00·P14와
같은 버전의 docs/redesign/design.md를 읽는다.
진행 상태는 기억이나 이전 채팅보다 실제 Git·검증 기록을 우선한다.
John의 시안 승인·구현 승인·운영 공개 승인은 서로 구분한다.
세션 종료 전 담당 Task의 결과 commit·검증·다음 단계를 인계한다.
```

규칙 파일 이름만 있다고 자동 적용을 보장하지 않는다. 새 세션에 두 파일을 실제로 읽게 하고, 현재 Task와 금지 영역을 요약하는지 확인한다. 웹 GPT의 새 대화에는 두 문서를 첨부하거나 접근 가능한 저장소 위치를 알려준다.

## P07. 개발 환경·데이터·공개 분리

| 환경 | 데이터·결제·발송 | 쓰기 제한 |
|---|---|---|
| Pencil/디자인 미리보기 | 샘플 상품·가짜 고객·실결제 없음 | `.pen`, 승인된 자산/문서만 |
| 로컬 기능 개발 | 테스트 DB 또는 승인된 격리 연결 | 운영 DB·실메일·실결제 접근 금지 |
| 통합 preview/staging | 테스트 Appwrite + PayPal Sandbox + 테스트 알림 수신자 | 접근 제한·검색 제외 확인 |
| Production | 실제 고객·상품·결제·발송 | 별도 공개 승인과 배포 절차 후만 변경 |

worktree는 코드만 분리한다. `.env`가 운영 DB를 가리키면 별도 branch도 실제 주문을 만들 수 있다. 운영 키는 일반 에이전트 작업 환경에서 제거/제한하고, 비밀값을 문서·Git·채팅·캡처에 넣지 않는다.

`.env.example`은 변수 이름과 안전한 예시만 다룬다. private key, 인증 token, 고객 이름/전화/이메일, 결제 원문, private 업로드 URL을 증거 파일로 복사하지 않는다.

Cloudflare Pages preview는 Git 설정에 따라 branch push로도 생성될 수 있다. Draft PR 상태 자체가 배포 차단이라고 가정하지 않는다. preview의 검색 제외도 인증/DB 격리를 대신하지 않는다. [P-S11]

Pencil 시안 승인 전 운영 자격증명을 로드하는 프로그램을 실행할 필요는 없다. 코드 테스트와 개발 서버도 실행 전 대상 연결을 확인한다.

## P08. 개발 전에 합의할 기능 계약

이 절은 **구현 시 필요한 계약 체크리스트**다. 여기의 개념 이름은 제안이며 현재 API에 이미 존재하는 새 필드/endpoint라고 주장하지 않는다. T04에서 기존 타입에 맞춰 정확한 입력·출력·오류와 파일 경계를 확정한다.

### 8.1 상품과 옵션

| 계약 | 확정할 내용 |
|---|---|
| 상품 식별 | 단품·세트·서비스 ID, 기존 ID 보존, 신규 ID 승인 |
| 표시 정보 | 이름, 설명, 사진, 캡션, 순위, 시트 특징, 판매 가능 여부 |
| 구매 방식 | 정가 주문인지 문의·견적형인지 |
| 변형/옵션 | 선택 ID, 필수 여부, 해당 상품 허용 여부, 수량 단위 |
| 세트 구성 | 세트 개수와 내용물 개수 분리, 5+1 구성, 포장 적용 |
| 금액 | AUD 정수 cents, 단가·할인·포장·배송·세금의 승인된 규칙 |
| 장바구니 identity | 같은 선택만 합쳐지는 key, 다른 포장/옵션은 구분 |
| 주문 snapshot | 주문 당시 상품명·구성·가격 보존, 과거 주문을 새 가격으로 다시 해석하지 않음 |

기존 cart에는 상품별 수량 규칙과 개별 포장 계산이 있다. 모든 신상품에 케이크 필드를 억지로 적용하거나 기존 모든 상품 타입을 일괄 바꾸지 않는다. [P-S06]

### 8.2 문의형 서비스

커스텀·기업 행사·카페 납품·컨설팅은 목적·연락처·일정·수량/규모·메모·필요한 사진을 받는 방향이다. 실제 필수값과 업로드 제한은 현재 시스템과 운영 정책에 맞춰 확정한다.

접수 완료는 가격 합의·예약 확정·결제 완료와 다르다. 관리자 표시와 고객 안내, 스팸 제한, 재시도 중복 접수를 함께 설계한다.

### 8.3 PayPal — 최소 설계 범위

PayPal 공식 표준 흐름은 프론트가 서버 endpoint를 통해 주문 생성과 capture를 요청하는 구조다. 이를 기존 AU 주문 저장·알림과 연결한다. [P-S12]

제안하는 경계:

```text
선택·수량 수집
→ 서버 상품/옵션·금액·가능 일정 검증
→ 내부 주문/결제 시도 기록
→ PayPal 주문 생성
→ 고객 승인
→ 서버 capture 및 결과 검증
→ 내부 결제 상태 반영
→ 정책에 따른 예약 확정/확인 중 안내
```

이 흐름의 슬롯 확보 시점·만료·대금 수납 시점·환불 책임은 Q11–Q14가 선행 결정한다. 자동 확정되지 않는 상품을 결제 성공만으로 제작 확정 처리하지 않는다.

안전 요구:

- 클라이언트의 합계·discount·상품명을 결제 금액의 신뢰 근거로 쓰지 않는다.
- 내부 주문 ID와 PayPal order/capture ID를 연결하고 금액·통화·수취 대상·상태를 확인한다.
- 동일한 작업 재시도에는 안정된 멱등 키를 사용한다. 금액/내용이 바뀐 요청에 이전 키를 재사용하지 않는다.
- `PayPal-Request-Id`의 지원 여부·보존 기간은 사용하는 API 문서에서 확인한다. 우리 DB의 중복 방지도 따로 구현한다. [P-S13]
- 웹훅 서명을 검증하고 실제 등록된 webhook ID와 환경을 사용한다. 미검증 이벤트로 주문을 paid로 바꾸지 않는다. [P-S14]
- webhook event ID, provider capture ID, 주문 상태 전이의 중복/경합을 처리한다.
- capture 응답과 webhook이 동시에 와도 주문 확정·고객 이메일이 두 번 발생하지 않게 한다.
- 결제 성공 후 내부 저장 실패·브라우저 종료·응답 유실은 확인 중 상태와 재조회/대사 경로를 갖는다.
- 웹훅은 검증·처리 또는 내구성 있는 접수 기록 없이 성공 응답만 보내고 잊지 않는다.
- 오래되거나 역순 이벤트가 완료 상태를 이전 상태로 되돌리지 않게 한다.
- 비회원 주문/결제 상태 조회도 주문 번호만 아는 타인에게 공개하지 않도록 소유 확인 수단을 설계한다.

예약 상태와 결제 상태를 구분한다. 기존 저장된 한국어 상태값/과거 reader를 일괄 치환하지 말고, 필요한 신규 상태와 기존 호환 관계를 명시한다.

**Stripe 준비:** 결제 서비스 연결 부분만 분리하고 내부 주문의 정체성을 PayPal ID에 종속시키지 않는다. Stripe 코드·키·공개 버튼은 이번 단계에서 만들지 않는다.

### 8.4 선택적 고객 로그인

목표는 재주문 시 이름·연락처 등 입력 부담을 줄이는 것이다. 비회원 주문을 유지한다. 포인트·등급·소셜 로그인·카드 정보 저장·구독·위시리스트는 현재 요청 범위가 아니다.

이메일 OTP는 Appwrite가 제공하는 후보지만 실제 self-hosted 버전과 발송 설정을 확인해야 한다. 선택되기 전 인증 방식이 확정됐다고 구현하지 않는다. [P-S15]

계약에 포함할 사항:

- 로그인 고객이 자신의 정보만 읽고 수정할 수 있는 권한.
- 일반 사용자 계정 생성이 관리자 API·DB 접근을 열지 않는지 검사.
- 인증 전후 cart 유지, 만료·로그아웃·다른 사용자 로그인 시 개인정보 분리.
- 이메일 문자열 일치만으로 과거 비회원 주문을 자동 연결하지 않는 소유 확인.
- 저장할 항목·수정 방식·이메일 변경·세션 지속·공유 기기 처리를 명시.
- 연락처를 동의 없이 localStorage 등에 무기한 저장하는 우회 구현 금지.
- 인증 실패·재전송·만료·오용 제한과 정상 비회원 주문 복귀.

### 8.5 기존 backend와 데이터 보존

새 필드·저장 형태가 필요하면 가능한 추가적 migration과 호환 reader를 우선 검토한다. 기존 주문 row나 가격 snapshot을 새 상품 규칙으로 덮어쓰지 않는다. 신규 프론트와 구 API, 구 프론트와 신 API의 배포 중간 상태를 계약 테스트로 다룬다.

운영 migration에 범용 setup 스크립트를 자동 사용하지 않는다. 변경할 자원·예상 diff·기존 권한·백업·복구 계획·적용 순서를 명시한 전용 절차를 승인받는다.

## P10. 실행 Task 상세

### 공통 Task 실행 방식

코드 Task는 해당 파일을 읽은 뒤 구체적인 변경·테스트 계획을 확정하고, 실패하는 테스트/재현을 먼저 확인 → 최소 수정 → 관련 테스트 → 통합 검증 → 명시한 파일만 commit한다. 아래 계획은 전체 개편의 관리 기준이며, Q 항목이 열려 있는 backend Task를 곧바로 코드로 옮기는 완성된 API 명세가 아니다.

새 backend module/endpoint 이름은 T04·T12·T14의 계약 결정 기록에 먼저 넣는다. 작업별 상세 계약과 실행 가능한 테스트는 해당 Task 승인 전에 이 계획의 작업 기록 또는 연결된 작업 문서에 추가한다.

### 11.2 기준 스크립트

기준 `package.json`에서 확인한 명령 이름을 참고한다. 실행 전 최신 스크립트와 네트워크/쓰기 영향을 읽고 테스트 환경임을 확인한다. 이 문서 작성에서는 아래 명령을 실행하지 않았다. [P-S07]

```bash
# 승인된 격리 작업 환경에서 실행할 검증 예시
npm run lint
VITE_MARKET=AU npm run test:cake
VITE_MARKET=AU npm run test:custom-cake-frontend
VITE_MARKET=AU npm run test:custom-cake-integration
VITE_MARKET=AU npm test
VITE_MARKET=AU npm run build
```

KR 검증은 별도 checkout 또는 안전하게 분리된 빌드 출력에서 수행한다.

```bash
VITE_MARKET=KR npm run build
git diff --check
```

`npm test`의 pretest와 개별 script의 market 동작을 확인한다. `test:cake`에 포함되지 않은 새 HOGIRL/기능 테스트가 있으면 명시적으로 추가 검증한다. 모든 테스트가 한 script에 자동 포함된다고 가정하지 않는다.

한 worktree의 동일 `dist`에 AU·KR 빌드를 동시에 쓰지 않는다. 재현을 위해 Node/npm 버전·lockfile·실제 명령·대상 commit·종료 코드·pass/fail/skip·환경 구분을 남긴다. 비밀 환경값은 남기지 않는다.

## P12. baseline·배포·rollback

### 12.1 baseline은 네 가지를 분리한다

| 기준 | 무엇을 보존하는가 |
|---|---|
| Git source baseline | 정확한 commit과 annotated tag |
| Frontend deployment baseline | Cloudflare deployment ID·환경·commit·아티팩트 |
| Backend baseline | 활성 function deployment·스키마·권한·설정의 비밀값 없는 식별 기록 |
| Data/media baseline | 기존 주문 데이터·원본 사진·스토리지의 승인된 백업/복구 방식 |

태그를 만들었다고 데이터베이스와 외부 사진까지 백업된 것은 아니다. 프론트 tag만 되돌려도 결제·DB·외부 발송 상태가 모두 이전으로 돌아가는 것이 아니다.

### 12.2 배포 계획에 반드시 포함할 것

- 신규 프론트/서버와 구버전이 공존하는 동안의 호환 창.
- 추가 스키마 생성·검증·backend 활성화·frontend 반영의 실제 순서.
- 어떤 변경은 되돌릴 수 있고 어떤 외부 효과는 되돌릴 수 없는지.
- 기존 주문과 새 결제 상태를 구버전 reader가 처리할 수 있는지.
- 실패 시 새 결제 시도를 중단하는 방법과 이미 받은 결제/webhook을 계속 처리하는 경로.
- 담당자·확인 명령·허용 대상·재개 승인 조건.

### 12.3 출시 후 확인

실제 확인은 승인된 운영 점검으로 수행한다. 본 문서에 기록하는 것만으로 자동 감시·알림이 설정되지는 않는다. 주문 실패·결제 미대사·이메일 실패·자산 누락·라우팅 오류·HOGIRL 공개 변화 여부를 누가 어떤 증거로 확인할지 출시 전에 정한다.

## P15. 변경 관리와 새 세션용 프롬프트

### 15.1 두 문서의 책임

`design.md`는 시각·페이지·Pencil 기준, `plan.md`는 상태·역할·정책 미정·검증·실행의 원장이다. 동일 정보를 두 곳에서 각각 새로 결정하지 않는다. 변경이 양쪽에 영향을 주면 같은 문서 변경 묶음으로 검토하고 버전을 맞춘다.

작업 branch의 문서는 오래될 수 있다. 시작·인계 때 최신 통합 문서 commit을 확인한다. 다른 사람의 작업본에 자동 복사하거나 수정 중인 파일을 덮지 않는다.

### 15.2 모든 에이전트 공통 시작 프롬프트

```text
AU-CAKE 리디자인을 이어서 진행한다.
```
