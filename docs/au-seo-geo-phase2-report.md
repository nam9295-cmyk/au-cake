## 성능 측정 조건

- 비교 경로는 홈, 케이크 목록, 파베 홀케이크, 초콜릿 모찌, 저널 목록, 저널 18편, 포트폴리오다. 각 빌드에서 7개 경로 × 2종 기기 × 3회를 측정했다.
- LCP·CLS·FCP·TBT는 Lighthouse 12.8.2와 Chromium 156.0.8078.4의 탐색 감사로 측정했다. 모바일/데스크톱 기본 시뮬레이션 설정에 동일한 500ms 네트워크·CPU 유휴 판정과 최대 로드 대기 12초를 적용했다. JS·이미지는 HTTP(S) 네트워크 행의 전송 바이트 합계, 요청 수는 해당 행 수다. 로컬 서버는 no-store이고 본문을 압축하지 않는다.
- TTFB는 별도 Chromium Navigation Timing에서 navigation 시작부터 responseStart까지 측정했다. 모바일은 390×844와 CPU 4배 감속, 데스크톱은 1440×900에서 캐시를 끄고 새 컨텍스트로 실행했다. 운영 도메인에는 같은 브라우저 관측을 적용했다. 운영 CDN의 압축·지연과 로컬 서버의 조건이 달라 두 표의 절댓값을 직접 비교하기 어렵다.
- PSI API가 일일 쿼터 초과(HTTP 429)를 반환했다. 이 점검에서는 CrUX의 URL 또는 origin 75백분위 LCP·CLS·INP를 확보하지 못했다. 표의 TBT는 실험실에서 관찰한 메인 스레드 차단 시간이다. 실사용자 목표인 LCP 2.5초, INP 200ms, CLS 0.1 달성 여부는 배포 후 실사용 데이터가 필요하다. [Core Web Vitals 기준](https://web.dev/articles/vitals)

## 홈 하트·팝업과 남은 성능 과제

로컬 후보에서 팝업을 표시한 경우와 이미 닫은 경우를 세 번씩 비교했다. 모바일 LCP 중앙값은 각각 492ms와 456ms, 데스크톱은 236ms와 116ms였다. 모든 경우의 CLS 중앙값은 0.001 미만이었다. 팝업 이미지는 일부 전송비용을 더하지만, 표시 중에는 Hero 동영상을 내려받지 않는다. 390px·1440px 모두 닫은 뒤 실제 영상 재생 시간이 증가하는 것을 확인했다.

팝업을 닫은 동일 조건에서 첫 홈 진입과 방문 기록이 있는 홈 진입도 비교했다. 모바일 LCP 중앙값은 각각 312ms와 336ms, 데스크톱은 둘 다 108ms였다. 이 표본에서 하트가 전환을 반복적으로 늦춘다는 증거는 찾지 못했다. 기존 구현은 첫 홈의 앱이 준비될 때까지 정적 콘텐츠를 가리며 500ms를 넘으면 하트를 표시한다. 최소 노출 시간을 강제하지 않는다. 느린 모듈, 모듈 다운로드 실패, JavaScript 비활성, 모션 줄이기, 상품 이동·뒤로 가기를 브라우저에서 점검했다. 하트, 팝업 디자인과 Hero 로딩 순서는 유지했다.

다음 성능 점검의 우선순위는 모바일 케이크 목록과 데스크톱 포트폴리오다. 케이크 목록은 기준 로컬 Lighthouse에서 CLS 0.281이었고, 포트폴리오는 운영 데스크톱 브라우저 표본에서 0.123이었다. 관련 글 매핑을 공용 앱에 넣은 첫 후보는 모든 화면의 초기 JS를 압축 전 약 3 KiB 늘렸다. 최종본은 매핑을 상품 카탈로그 번들로 옮겨 홈과 포트폴리오에서 이 데이터를 내려받지 않도록 했다. 느린 모바일 조건에서 기존 상품 페이지의 큰 초기 번들과 이미지 비용도 남아 있다. 운영 포트폴리오 추가 추적에서 그리드·이동 링크·사진 캡션이 포함된 한 번의 이동이 0.122를 차지했다. 원인을 구분하려면 정적 화면이 앱으로 교체되는 시점, 폰트와 주요 이미지의 실제 레이아웃 이동을 운영 환경에서 추적해야 한다.

## 검색 정책과 검증 범위

- 저장소 및 운영 robots.txt에서 Googlebot, Bingbot, OAI-SearchBot, Applebot의 공개 경로 접근을 확인했다. 네 User-Agent로 홈·저널을 요청한 8건이 모두 HTTP 200이었다. 실제 검색 서비스의 IP·크롤 기록이나 색인 판정은 별도다. 운영 응답의 Cloudflare 관리 구역은 GPTBot, Google-Extended, ClaudeBot, Applebot-Extended에 Disallow를 제공하며 저장소에는 search=yes, ai-train=no, use=reference가 선언돼 있다. 보호 경로용 X-Robots-Tag와 배포 설정을 유지했다. [운영 robots.txt](https://au.verygood-chocolate.com/robots.txt)
- 파베와 바스크는 기존 Product/Offer가 실제 가격 계산 결과와 선택 주소를 제공한다. 바스크는 하나의 상품 경로에 홀·로프가 함께 있고, 현재 구조만으로 모든 사이즈·마감 조합의 고유 variant 식별과 상품 그룹 피드 운영 근거가 충분하지 않다. 이번에는 ProductGroup 전환을 보류했다. 승인 전 옵션의 가격·재고를 새로 추정하지 않았다. [Google 상품 변형 가이드](https://developers.google.com/search/docs/appearance/structured-data/product-variants)
- llms.txt는 기존 정보의 보조 목록이다. 검색·생성형 답변에 노출되는지는 검색 서비스의 색인과 선택에 달려 있다. 이번에 변경한 부분의 직접적인 효과는 판매 종료, 작성 주체, 관련 기사 정보를 최초 HTML에서도 읽을 수 있다는 점이다. [Google 검색의 AI 기능 안내](https://developers.google.com/search/docs/appearance/ai-features)

## 검증 결과

- `npm test` 출력의 하위 테스트 합계는 통과 2,411, 실패 0이었다. AU 실행에서 생략한 KR 전용 테스트 1개는 별도 KR 빌드에서 실행해 통과했다. 저널 61개와 고객 계정 422개가 이 합계에 포함된다. 카탈로그 링크 위치를 확정한 뒤 관련 상품, 고객 계정, 커스텀 케이크 통합 테스트와 ESLint도 다시 통과했다.
- AU 빌드는 `VITE_MARKET=AU VITE_CUSTOMER_ACCOUNT_ENABLED=true npm run build`, KR 빌드는 별도 디렉터리에서 `VITE_MARKET=KR npm run build`로 실행했다. 기준 빌드에서도 발생하던 PostCSS의 from 옵션 경고와 Vite의 500 kB 초과 청크 경고는 남아 있다.

- AU 계정 기능 활성 프로덕션 빌드와 별도 KR 프로덕션 빌드가 성공했다. KR 빌드에는 AU 저널 카탈로그·저널용 llms 목록이 없고 기존 KR 정적 상품 경계 테스트를 통과했다.
- AU sitemap의 URL 45개에서 JSON-LD 블록 58개를 파싱했다. 최초 HTML에서 찾은 서로 다른 내부 링크 경로 46개가 모두 로컬 HTTP 200이었다. 상품 관련 링크 6개 영역, 저널 카탈로그, RSS와 sitemap을 대조했다. 6개 상품·컬렉션과 할로윈 페이지에서 최초 HTML과 앱 실행 후의 제목·canonical·Open Graph·Twitter 등 9개 필드가 일치했고, 잘못된 경로는 HTTP 404였다. 외부 검색엔진의 리치 결과 적격 판정은 이번 검사 범위 밖이다.
- 저널 18편 전부 기존 운영 주소가 HTTP 200이었다. 로컬에서 JavaScript를 끄고 방문한 22개 경로(18편, 홈, 저널 목록, 할로윈, 파베)의 제목이 표시됐다. 첫 홈 모듈 다운로드 실패 시에도 정적 홈 제목이 표시됐다.
- Chromium 데스크톱과 iPhone WebKit에서 상품 옵션·관련 링크·기사 이동, 첫 홈·재방문, 실패한 상품 모듈의 수동 재시도를 확인했다. 가격·예약·결제는 기존 회귀 테스트로 확인했으며, 운영 주문이나 결제는 생성하지 않았다.
- 판매 종료 시각과 그 직후를 각각 테스트했다. 정적 페이지는 빌드 당시 상태를 가지므로 향후 시즌 종료 시에는 마감 직후 AU 사이트를 다시 빌드·배포해야 한다. 같은 시즌 설정에 실제 마감 판정·픽업일을 등록할 수 있다.
- 병합·운영 배포, Cloudflare 정책 변경, Search Console 색인 요청은 실행하지 않았다. 배포 승인 후 확인할 대상은 운영 저널 작성자·관련 글, 할로윈 마감 안내와 Offer 제거, llms.txt의 최신 18편이다.
